# SynkaCore V1.2 — Buffer Local, Resiliência Estrutural e Simulação de Processo

**Status:** Concluída
**Data:** Maio 2026

---

## Objetivo da versão

A V1.1 entregou resiliência reativa: o sistema tenta reconectar, abre circuit breaker e protege o banco durante recuperação. Funciona para quedas de segundos. A V1.2 endereça o cenário que a V1.1 não cobre: queda prolongada do TimescaleDB.

Em ambiente industrial real, "queda prolongada" é o caso comum. Manutenção de banco, troca de servidor, falha de disco, interrupção de rede entre fábrica e datacenter, todos esses cenários duram minutos ou horas. Um middleware que perde dados durante esses períodos não é viável em produção.

A V1.2 garante zero perda de dados durante qualquer queda de duração, independente de tempo.

Adicionalmente, a V1.2 substitui dados aleatórios por simulação fiel de processo industrial (câmara de vácuo de curtimento), preparando a apresentação técnica do middleware para conversas com clientes potenciais antes do hardware real estar disponível.

## O que entrou nesta versão

### Buffer local em SQLite

`SensorReadingLocalBufferRepository` persiste leituras em arquivo SQLite quando o TimescaleDB está indisponível. Quando o primário volta, as leituras são sincronizadas em ordem cronológica.

Tabela `pending_readings` em arquivo `buffer/synkacore_buffer.db` (configurável):

```sql
CREATE TABLE IF NOT EXISTS pending_readings (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TEXT    NOT NULL,
    tag       TEXT    NOT NULL,
    value     TEXT    NOT NULL,
    unit      TEXT    NOT NULL,
    synced    INTEGER NOT NULL DEFAULT 0
);
```

### Decorator Pattern para orquestração

`ResilientReadingRepository` implementa `ReadingRepository` e recebe duas dependências: o repositório primário (TimescaleDB) e o buffer local. Toda a lógica de fallback e sincronização vive no decorator.

O Worker não muda. Ele continua chamando `repository.save(reading)` sem saber que existe SQLite, sem saber sobre fallback, sem saber sobre sincronização. Decorator é detalhe de infraestrutura.

### Interface ReadingRepository

Abstração no Domain para que o Worker dependa de contrato, não de tecnologia concreta:

```java
public interface ReadingRepository {
    void save(SensorReading reading) throws Exception;
    void checkHealth() throws Exception;
}
```

Implementações: `SensorReadingRepository` (TimescaleDB) e `ResilientReadingRepository` (decorator). O container entrega o decorator (marcado `@Primary`) quando alguém pede `ReadingRepository`.

### WorkerStateTracker compartilhado

Estado do Worker (CONECTADO, RECONECTANDO, DEGRADADO) movido para um serviço singleton dedicado. Permite que os event listeners do Resilience4j atualizem o estado sem depender do tipo concreto do Worker, e que múltiplos consumidores (Worker, futuros health checks, dashboards) leiam o estado de forma thread-safe.

Enum `WorkerState` movido para `synkacore-domain` para evitar dependência circular Collector → Infrastructure → Collector.

### Pipeline Resilience4j com injeção de dependência

`DatabaseResiliencePipelineBuilder` encapsula a construção da pipeline. Os event listeners (`onStateTransition` do circuit breaker e `onRetry` do retry) recebem `WorkerStateTracker` via injeção de dependência, atualizando o estado do Worker e logando com formatação consistente.

Substitui o uso de logger estático nos callbacks que existia na V1.1.

### Validação de OpcUaSettings

`OpcUaSettings` é anotado com `@Validated` e valida no startup que `endpoint-url`, `node-id` e `tag-name` estão presentes (`@NotBlank`) e que `interval-ms >= 100` (`@Min`). Falha rápida com mensagem clara.

### BufferSettings configurável

`database-path` e `sync-batch-size` saíram de constantes hardcoded para `application.yml`. Hardware com folga aumenta `sync-batch-size` para drenar buffer mais rápido. Hardware limitado reduz para 5 ou menos.

### Simulação de processo industrial real

`VacuumChamberSimulator` substituiu o uso de dados aleatórios no Worker. Implementa `ProtocolReader` para modelar uma câmara de vácuo de curtimento com ciclo realista:

| Fase | Duração | Comportamento |
|---|---|---|
| Ocioso inicial | 0-30s | Ambiente ~25°C |
| Aquecimento | 30-60s | Rampa linear 25°C → 65°C |
| Manutenção | 60-120s | ~65°C com ruído realista de ±0.8°C |
| Resfriamento | 120-150s | Rampa linear 65°C → 25°C |
| Ocioso final | 150-180s | Ambiente ~25°C |

O Worker não sabe que está lendo de um simulador. Em V1.3+ basta trocar o bean no DI para `OpcUaProtocolReader` apontando para hardware real ou servidor OPC UA simulado.

### IntervalMs respeitado pelo Worker

Worker agora lê `OpcUaSettings.intervalMs()` do `application.yml` em vez de um intervalo hardcoded. O validador garante valor mínimo de 100ms.

### Conexão e desconexão graciosa do ProtocolReader

Worker chama `connect()` no startup e `disconnect()` durante shutdown. Falha de conexão no startup é tratada como erro crítico: o sistema loga e encerra com mensagem clara em vez de loop infinito.

A interrupção da thread é capturada separadamente para permitir shutdown limpo sem entrar em estado DEGRADADO desnecessariamente.

## Bugs críticos corrigidos durante a V1.2

A V1.2 começou como adição do buffer SQLite mas evoluiu para versão de correção estrutural após auditoria completa do código. Três bugs críticos foram identificados e corrigidos.

### Bug 1: Worker bypassando o decorator

O `SensorCollectorWorker` recebia `SensorReadingRepository` (tipo concreto, TimescaleDB direto) em vez de `ReadingRepository` (decorator). Resultado: todo o sistema de buffer estava registrado no container mas nunca era usado. Quando o banco caía, dados eram perdidos exatamente como na V1.1.

Causa: ao implementar o decorator, o tipo do parâmetro do construtor do Worker não foi atualizado para a interface.

Correção: Worker recebe `ReadingRepository`. O container entrega o `ResilientReadingRepository`, marcado `@Primary`. O repositório primário é injetado no decorator apenas pelo tipo concreto, nunca como `ReadingRepository`.

### Bug 2: Estado RECONECTANDO via fragmento de string

O bloco original:

```java
catch (Exception ex) {
    if (ex.getMessage().contains("tentativa"))
        state = WorkerState.RECONECTANDO;
}
```

Dependia da exceção da pipeline conter a palavra "tentativa" na mensagem. Mas a exceção não inclui esse texto — ele aparece somente no event listener `onRetry`. O filtro nunca casava. O estado RECONECTANDO era código morto.

Correção: os event listeners chamam `WorkerStateTracker.notifyRetrying()` diretamente. Estado é atualizado pela fonte real do evento.

### Bug 3: Leitura corrompida travando sincronização

`syncBuffer` chamava `pendingReading.toSensorReading()` que pode lançar exceção em decimal ou timestamp mal formado. A exceção era capturada e o `break` parava o ciclo, mas a leitura corrompida nunca era marcada como sincronizada. Todo ciclo futuro tentaria o mesmo item e falharia no mesmo ponto.

Correção: parsing isolado em try/catch separado. Se a conversão falhar, a leitura é marcada como `synced = 1` com log de erro para auditoria, e o ciclo continua.

## Outras correções importantes

### Cancelamento cooperativo no shutdown

O Worker respeita a interrupção da thread durante a coleta e durante o intervalo (`Thread.sleep`), garantindo cancelamento limpo durante o shutdown sem perder o ciclo em andamento.

### Formatação independente de locale no buffer

Bug latente que se manifestaria em produção: salvar um decimal em locale `pt-BR` poderia gerar `"72,5"` com vírgula, e recuperá-lo esperando ponto falharia silenciosamente. No buffer, `value` e `timestamp` são gravados como TEXT usando `BigDecimal(String)` e ISO-8601 (`OffsetDateTime`), que são independentes de locale por natureza, eliminando o risco.

### ModbusProtocolReader implementa ProtocolReader

Classe vazia substituída por stub que implementa o contrato e lança `UnsupportedOperationException` com mensagem explicativa. Garante que tentativa de uso falha no compilador (se a interface mudar) e em tempo de execução com mensagem clara.

### Sistema falha ruidosamente quando primário e buffer falham

`ResilientReadingRepository` agora re-lança a exceção quando ambos os destinos falham. O Worker entra em estado DEGRADADO e o log de erro CRÍTICO é emitido. Sistema industrial que perde dados em silêncio é pior que sistema que falha visivelmente, porque o operador não sabe que há problema.

### Re-lançamento preserva a exceção original

A exceção é re-lançada como está, preservando o stack trace original em vez de envolvê-la em outra exceção que dificultaria o debug.

### Logs renomeados para `synkacore-collector-*.log`

Simetria com `synkacore-api-*.log` da Api. Facilita identificação em sistemas multi-componente.

## Decisões técnicas com justificativa

### Por que SQLite e não outro banco embutido

SQLite é o banco embutido mais usado no mundo, presente em sistemas industriais críticos (aviônica, automotivo, marítimo). Tem mais de 25 anos de produção, ACID por design, sem servidor para gerenciar, arquivo único portável, e zero custo de licença. Para buffer local em edge computing, é a escolha óbvia.

H2 em modo embarcado foi considerado, mas o SQLite tem footprint menor e garantias formais de durabilidade mais consolidadas em ambiente edge.

### Por que append-only sem deleção

Leituras com `synced = 1` não são deletadas. Mantém histórico permanente para auditoria, diagnóstico de incidentes e análise de quedas. Custo de disco é desprezível comparado ao valor de poder investigar o que aconteceu durante uma queda passada.

Política de retenção futura (V1.7+) vai permitir arquivar leituras antigas, mas o default permanece append-only.

### Por que value e timestamp como TEXT no SQLite

SQLite não tem tipo de data/hora com offset nativo nem suporta decimal com precisão arbitrária (`REAL` é ponto flutuante internamente). Armazenar como `TEXT` no formato ISO 8601 para timestamp e string decimal (`BigDecimal`) preserva precisão exata.

### Por que sincronizar buffer dentro de save do decorator

Alternativa seria um serviço agendado separado (`@Scheduled`) com timer. Foi rejeitada para V1.2 porque adiciona complexidade de threads e coordenação que não justifica o ganho. Sincronizar oportunisticamente após cada gravação bem-sucedida é suficiente: durante operação normal o buffer está vazio, durante queda o buffer enche, durante recuperação ele drena a cada gravação que passa.

Anotado como débito técnico para V1.3+ se medições reais indicarem que o tempo de sync está afetando o ciclo do Worker.

### Por que SyncBatchSize default 10

Conservador. Drena 10 leituras a cada gravação bem-sucedida no primário. Com leituras a cada 2 segundos, isso significa 10 leituras drenadas a cada 2 segundos, ou 300 leituras por minuto.

Para queda de 1 hora a 1Hz de coleta, gera ~3600 leituras pendentes. Drenar a 300/min leva 12 minutos para recuperação completa. Aceitável.

Hardware com mais folga aumenta para 50 ou 100. Configurável via `application.yml`.

### Por que volatile em vez de lock no WorkerStateTracker

O estado é um único campo `volatile`, garantindo leitura cross-thread atômica sem cache local. Para a maioria das transições (escrita simples), isso é suficiente e mais leve que um lock. O bloco de transição é protegido apenas para que a comparação "mudou de estado?" e o log da mudança sejam consistentes.

### Por que enum WorkerState no Domain

Inicialmente o enum vivia no Collector. Quando o `WorkerStateTracker` foi criado no Domain, o tipo de retorno `currentState()` precisaria referenciar `WorkerState` do Collector, criando ciclo Domain → Collector → Domain.

Solução: enum movido para Domain. Estados do Worker são conceito de domínio (operacional vs degradado), não detalhe de implementação. O lugar correto é o Domain.

### Por que DatabaseResiliencePipelineBuilder em vez de configurar pipeline inline

Os event listeners da pipeline precisavam acessar `WorkerStateTracker` e um logger. Encapsular num builder injetado via DI permite que os listeners recebam dependências normalmente e fica testável.

### Por que simulação por fases lineares em vez de modelo físico completo

Modelo físico real de transferência de calor exigiria equações diferenciais (lei de resfriamento de Newton, ou modelo termodinâmico de câmara de vácuo). Para o propósito da V1.2 — gerar dados que se parecem com processo industrial real — interpolação linear entre fases definidas é suficiente. O ruído gaussiano adicionado simula incerteza de instrumento.

V1.3+ pode evoluir para modelo físico se houver necessidade técnica de validação contra dados reais de equipamento.

### Por que cycleStart inicializado em connect e não no construtor

`connect()` espelha o comportamento de equipamento real: a sessão começa quando o cliente conecta, não quando o objeto é construído. Reiniciar o simulador com `disconnect()` + `connect()` reinicia o ciclo, comportamento esperado e útil para testes.

## Débitos técnicos identificados e anotados

Da auditoria completa do código, alguns pontos foram identificados como débito mas adiados para versões futuras:

**Sincronização do buffer dentro de save pode aumentar latência do Worker em casos extremos.** Se houver 1000 pendências e o sync demorar, o próximo ciclo do Worker espera. Mitigação na V1.3+: mover para um serviço agendado separado se medições indicarem problema.

**Health check da Api não reflete estado do Worker.** Api e Collector rodam em processos separados. Comunicar estado exige IPC ou banco compartilhado. Adiado para V1.5 quando Prometheus for implementado.

**Capacidade do middleware não validada por load test.** Estimativa conservadora: 3 a 5 dispositivos simultâneos com 1 leitura/segundo cada. Load test formal será feito antes de qualquer uso em produção real.

**OpcUaProtocolReader não exercitado.** Existe no código mas não é registrado no DI atual. Será exercitado em V1.3+ quando servidor OPC UA simulado (Prosys ou similar) for configurado.

Trade-offs detalhados estão documentados em `TRADE-OFFS.md`.

## Comportamento validado em teste de queda completa

Cenário testado: Collector rodando, banco TimescaleDB derrubado via `docker stop` por 60 segundos, depois `docker start`.

1. Collector inicia e conecta ao simulador VacuumChamber
2. Worker grava normalmente no TimescaleDB com dados em ciclo realista
3. `docker stop synkacore-timescaledb`
4. Próxima gravação falha. A pipeline tenta retry 1/3, 2/3, 3/3 com backoff exponencial
5. Retries esgotados. Decorator captura exceção e redireciona para buffer SQLite
6. `WorkerStateTracker` recebe `notifyDegraded()` do event listener do circuit breaker
7. Worker continua coletando. Leituras vão para `buffer/synkacore_buffer.db`
8. Após 30 segundos, circuit breaker entra em half-open, tenta uma gravação no primário
9. Banco ainda fora. Volta para open
10. `docker start synkacore-timescaledb`
11. Próxima half-open passa. Circuit breaker fecha. `notifyConnected()` disparado
12. Próxima gravação no primário sucede. Decorator chama `syncBuffer`
13. 10 leituras drenadas do buffer e gravadas no TimescaleDB em ordem cronológica
14. Próxima gravação drena mais 10. E assim por diante até buffer vazio

Nenhuma leitura perdida. Histórico contínuo no TimescaleDB após sincronização completa.

## Próxima versão

V1.2 finaliza o middleware funcionalmente para o escopo planejado. V1.3+ trará incrementos sob demanda: simulação de Modbus TCP, integração com servidor OPC UA real ou simulado (Prosys), métricas via Prometheus, e contrato MQTT para comunicação com SynkaStudio.

A partir da V1.2, o foco de desenvolvimento se desloca para o SynkaStudio (backend Java + frontend Angular). O SynkaCore permanece em manutenção e evolução incremental.
