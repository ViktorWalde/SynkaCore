# SynkaCore V1.1 — Resiliência e Observabilidade

**Status:** Concluída  
**Data:** Maio 2026

---

## Objetivo da versão

A V1.0 entregou o caminho feliz: coleta, persistência e API funcionando. A V1.1 torna o sistema confiável para operação contínua em ambiente industrial, onde falhas de rede, quedas de banco e interferências eletromagnéticas são realidade, não exceção.

---

## O que foi implementado

### Resiliência com Resilience4j

Pipeline de resiliência composta com três estratégias em ordem de execução: CircuitBreaker → Retry → Timeout.

**Circuit breaker por taxa de falhas**
- Abre quando 50% das chamadas falham em janela de 30 segundos
- Mínimo de 10 chamadas para ter amostra estatística válida
- Permanece aberto por 30 segundos antes de testar recuperação
- Transições de estado (OPEN, CLOSED, HALF_OPEN) logadas via event listeners

Escolha de 50% em vez de 100%: em ambiente industrial, metade das gravações falhando já indica problema real. Esperar 100% significa que o banco está completamente derrubado antes de protegê-lo.

**Retry com backoff exponencial e jitter**
- 3 tentativas com delays de ~2s, ~4s, ~8s
- Jitter de ±20% para evitar thundering herd em múltiplas instâncias
- Cada tentativa logada com número da tentativa e delay real

**Timeout por tentativa**
- 5 segundos por tentativa individual
- Operações normais de banco levam menos de 100ms — 5 segundos é generoso para rede industrial lenta mas rígido o suficiente para não travar o Worker

Documentação: https://resilience4j.readme.io/docs/getting-started

### Três estados do Worker

O Worker rastreia e loga seu estado operacional atual.

```java
public enum WorkerState {
    CONECTADO,
    RECONECTANDO,
    DEGRADADO
}
```

Campo `volatile` para garantir que leituras de outras threads (como o endpoint `/health`) sempre vejam o valor mais recente sem cache local da thread.

Transições logadas apenas na mudança de estado para evitar ruído nos logs.

### Observabilidade com SLF4J/Logback

Substituiu o logging padrão por configuração estruturada em `logback-spring.xml`. Carregada antes do contexto para capturar erros de inicialização.

**Saídas configuradas:**
- Console com template `[HH:mm:ss LVL] Logger: Message`
- Arquivo em `logs/synkacore-*.log` com rotação diária e retenção de 7 dias

**Enriquecimento:**
- Nome da máquina (`HOSTNAME`) incluído no padrão do arquivo de log, identificando a origem em ambientes multi-instância
- MDC (`Mapped Diagnostic Context`) disponível para propriedades adicionadas por contexto de execução

**Supressão de ruído:**
- `org.springframework` no nível Warning — suprime logs verbosos do framework
- Ciclo de vida da aplicação mantido em Information para ver startup e shutdown

Decisão de usar logger estático nos event listeners do circuit breaker na V1.1: os listeners são registrados durante a construção da pipeline, antes do container estar pronto. Refinado na V1.2 para receber dependências via injeção.

Documentação: https://logback.qos.ch/manual/

### Health check real

O endpoint `/health` executa `SELECT 1` no banco antes de responder. Retorna HTTP 200 com `database: connected` ou HTTP 503 com `database: unavailable`.

Retornar `healthy` quando o banco está fora é ativamente enganoso para sistemas de monitoramento e operadores de plantão.

### Validação de configuração no startup

`PostgresSettings` é anotado com `@ConfigurationProperties` + `@Validated`. Se `url` estiver ausente ou vazia (`@NotBlank`), o sistema falha imediatamente no startup com mensagem clara, em vez de subir e falhar silenciosamente durante operação.

Habilitado em ambos os módulos (Collector e Api) via `@EnableConfigurationProperties`.

Documentação: https://docs.spring.io/spring-boot/reference/features/external-config.html

### Mapeamento de persistência tipado

`SensorReadingQueryRepository` mapeia as colunas do banco para o record `SensorReading` via `RowMapper` tipado. O mapeamento por nome de coluna elimina casts manuais e move erros para tempo de compilação.

## Decisões técnicas relevantes

**Por que CircuitBreaker vem antes do Retry na pipeline**

A pipeline é executada de fora para dentro. O CircuitBreaker supervisiona o conjunto. Se ele está aberto, a chamada falha imediatamente sem nem chegar ao Retry. Sem isso, o Retry martelaria um banco inacessível desperdiçando tempo e agravando a sobrecarga durante recuperação.

**Por que taxa de falhas em vez de contagem simples**

Contagem simples (3 falhas seguidas) abre o circuit breaker com uma amostra mínima. Em rede industrial com interferências esporádicas, 3 falhas não indicam necessariamente problema sistêmico. Taxa de 50% em 30 segundos com mínimo de 10 chamadas exige evidência estatística antes de proteger o banco.

**Por que jitter no backoff exponencial**

Sem jitter, múltiplas instâncias que falharem ao mesmo tempo tentarão reconectar nos mesmos instantes. Com jitter de ±20%, os intervalos se distribuem, reduzindo a carga no banco durante recuperação.

## Débitos técnicos anotados

O `protocolReader` no Worker está injetado mas ainda não exercitado em coleta real. Intencional até V1.3, quando Modbus TCP for implementado. Anotado como débito.

Logger estático nos event listeners do circuit breaker usa formatação diferente do logger injetado no restante do sistema. Aceitável na V1.1 porque é uma limitação do momento de configuração, não uma escolha de design — resolvido na V1.2.

## Resultado validado

Sistema testado com queda forçada do banco via `docker stop`. Comportamento observado:

1. Falha detectada na primeira tentativa de gravação
2. Retry 1/3 após ~2 segundos
3. Retry 2/3 após ~4 segundos
4. Retry 3/3 após ~8 segundos
5. Worker entra em estado DEGRADADO, loga o erro, continua o loop
6. Banco restaurado via `docker start`
7. Próxima gravação bem-sucedida — Worker transita para CONECTADO
8. Log "Worker estado: DEGRADADO -> CONECTADO"

O Worker nunca morreu. Nenhuma intervenção manual foi necessária para recuperação.
